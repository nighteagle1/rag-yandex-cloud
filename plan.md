# Задание: RAG-ассистент по документации Yandex Cloud

## Цель
Собрать за минимальное время работающий проект: RAG-ассистент для первой линии поддержки на русскоязычной документации Yandex Cloud, собранный в Langflow, с трассировкой в Langfuse и воспроизводимой оценкой качества. Результат должен показывать цифры: сколько ответов верных, сколько галлюцинаций, как это менялось от эксперимента к эксперименту.

## Стек
| Задача | Инструмент |
|---|---|
| Генерация ответов, генерация вопросов, судья | OpenRouter, Chat Completions (OpenAI-совместимый, базовый URL `https://openrouter.ai/api/v1`), клиент — пакет `openai` |
| Эмбеддинги | OpenRouter, эндпоинт эмбеддингов, многоязычная модель |
| Векторное хранилище | Qdrant, косинусная метрика |
| Цепочка | Langflow |
| Трассировка | Langfuse Cloud, подключение через переменные окружения |
| Скрипты | Python 3.11+, `pandas`, `qdrant-client`, `openai`, `tqdm`, `python-dotenv` |

ID моделей в OpenRouter меняются. Не выбирай их по памяти: получи актуальный список через API или сайт OpenRouter, выбери и запиши в `README` три роли: дешёвая модель для ответов, более сильная модель для генерации вопросов и судьи, модель эмбеддингов. Для эмбеддингов проверь на 5 русских парах «вопрос — релевантный абзац», что модель различает близкие и далёкие тексты.

## Что нужно от человека до старта
Ключ OpenRouter, ключи Langfuse Cloud (public, secret, host). Если в среде нет Docker, ещё URL и ключ кластера Qdrant Cloud (бесплатный тариф). Всё кладёшь в `.env`, файл в git не попадает, ключи нигде не печатаются.

## Структура репозитория
```
yc-support-assistant/
├── README.md
├── .env.example
├── docker-compose.yml        # только Qdrant, если есть Docker
├── docs/requirements.md
├── scripts/  common.py  prepare_corpus.py  ingest.py  gen_questions.py  run_eval.py  judge.py
├── prompts/  v1.md  v2.md
```

`common.py` содержит клиенты OpenRouter и Qdrant, загрузку `.env`, функцию эмбеддингов. Корпус в репозиторий не коммитить, `corpus/` в `.gitignore`.

## Шаги
Коммит после каждого шага. По окончании отмечай задачу в списке задач.

**Шаг 1. Каркас и требования (15 мин).** Создай структуру и `docs/requirements.md` на одну страницу: пользователь (специалист первой линии поддержки облачного провайдера), что в рамках (вопросы по выбранным сервисам), что вне рамок (другие сервисы, юридические вопросы, инструкции вне документации), как выглядит хороший ответ (кратко, по контексту, со ссылкой на страницу). Метрики с порогами: верных ответов на вопросы с ответом в базе не меньше 80%; корректных отказов на вопросы без ответа не меньше 90%; ссылка на источник в каждом ответе; нужная страница в топ-5 найденных чанков не меньше 85%. Пороги фиксируются до первого замера.

**Шаг 2. Корпус (30–40 мин).** Склонируй `yandex-cloud/docs` с `--depth 1`, запиши хеш коммита в `README`. Найди каталоги с русской документацией. Выбери 4 сервиса: Compute Cloud, Object Storage, VPC и раздел тарификации/биллинга. Если структура другая, подбери аналоги, цель — 300–500 страниц с лимитами, ценами, процедурами и сетевыми настройками. `prepare_corpus.py` читает `.md`, удаляет front matter, разворачивает или удаляет конструкции YFM (`{% note %}`, `{% list tabs %}`, `{% include %}` и подобные), сохраняет для каждой страницы `title`, `service`, `url` и текст. URL собери по пути файла (`https://yandex.cloud/ru/docs/...`) и проверь на трёх страницах через WebFetch, что ссылки открываются. Просмотри 15 случайных очищенных страниц: остатков разметки быть не должно. В `README` запиши число страниц и токенов.

**Шаг 3. Индексация в Qdrant (30 мин).** `ingest.py` с параметрами `--chunk-size` и `--collection`. Разбиение по заголовкам Markdown, затем по размеру с перекрытием 100 токенов. В payload: `url`, `title`, `service`, `chunk_index`, `text`. Размерность коллекции возьми у выбранной модели эмбеддингов. Построй две коллекции: `yc_c1000` (размер чанка 1000) и `yc_c500` (500). Перед запуском выведи оценку числа токенов и стоимости и убедись, что она разумная. Проверка: поиск по трём вопросам возвращает релевантные страницы.

**Шаг 4. Поток в Langflow (до 1 часа, с ограничением).** Установи и запусти Langflow. Собери один поток: Chat Input → эмбеддинг вопроса через OpenRouter (компонент эмбеддингов с пользовательским базовым URL) → компонент Qdrant (top_k = 5, имя коллекции параметром) → сборка промпта (текст из `prompts/`) → модель OpenRouter (температура 0) → Chat Output. Ответ должен включать список найденных URL. Подключи Langfuse через переменные окружения. Собирай поток через REST API Langflow: возьми шаблоны компонентов и создай поток запросом. Экспортируй JSON в `flows/answer.json`. Проверь вызов `POST /api/v1/run/<flow_id>` из Python; параметры вроде коллекции и текста промпта переопределяй через `tweaks`, если это работает в установленной версии.

Ограничение по времени: если после трёх серьёзных попыток поток не собирается автоматически, остановись. Напиши в `docs/langflow-flow.md` точную спецификацию (компоненты, поля, соединения) для ручной сборки в интерфейсе, а пока реализуй запасной `scripts/answer.py` с той же логикой (поиск, промпт, генерация, логирование в Langfuse), чтобы не блокировать шаги 5–7. Сообщи человеку об этом сразу.

**Шаг 5. Тестовые вопросы (40–50 мин).** `gen_questions.py`: возьми случайные страницы из корпуса по всем четырём сервисам, сильная модель генерирует вопросы в формулировках живых сотрудников поддержки (включая неточные и разговорные). Состав, 40 строк: 10 фактов из одной страницы, 8 процедур, 5 на несколько страниц, 6 с числами (лимиты, цены, сроки), 8 без ответа в корпусе, 3 не по теме или с попыткой сбить инструкцию. Для вопросов без ответа проверь поиском по всему корпусу, что ответа действительно нет. Поля `questions.csv`: `id`, `type`, `question`, `gold_answer` (коротко), `gold_urls`, `should_refuse`, `split`. В `split` 30 строк `dev` и 10 `holdout` (holdout не смотреть при правке промптов). Проверь сам: все эталоны сверены со страницами, а не только сгенерированы.

**Шаг 6. Оценка (1 час).**
- `run_eval.py --config <name>` прогоняет вопросы. Режимы: `norag` (тот же вопрос той же модели без поиска), `rag` (вызов потока Langflow или `answer.py` с указанием коллекции и промпта). В `data/results/<config>.csv` сохраняй вопрос, ответ, найденные URL, время, id трейса. Для `rag` отдельно считай hit@5 и MRR по совпадению URL с `gold_urls`, запрашивая Qdrant напрямую.
- `judge.py`: сильная модель ставит ответу одну из меток `верно`, `частично`, `неверно`, `галлюцинация`, `корректный_отказ`, `некорректный_отказ` по рубрике из `prompts/judge.md` (сравнение с эталоном и с найденным контекстом). Выведи таблицу метрик и разбивку по типам вопросов.
- Человек вручную проверяет 20 меток судьи. Скрипт выводит эти 20 случайных строк в отдельный CSV и после заполнения считает долю совпадений.

**Шаг 7. Эксперименты (30–40 мин работы, остальное время на прогоны).** Все с температурой 0.
- A: без поиска.
- B: `yc_c1000`, промпт v1 («отвечай по контексту и укажи ссылку»).
- C: `yc_c1000`, промпт v2 (добавлено: если в контексте нет ответа, скажи об этом, не додумывай, ссылки только на найденные страницы).
- D: `yc_c500`, промпт v2.
Лучшую конфигурацию прогони ещё дважды, чтобы оценить разброс. Результаты запиши в таблицу в `README` (разделы «Эксперименты» и «Разброс»): что менялось, метрики на dev и на holdout, вывод одной фразой. Если различие меньше разброса, так и напиши. Не подгоняй промпты под holdout.

**Шаг 8. README (20 мин).** Разделы: задача и требования (ссылка на `docs/requirements.md`), архитектура одной схемой (Mermaid), выбранные модели и причины, как запустить с нуля, таблица экспериментов, известные ограничения (привязка к коммиту документации, размер выборки в 40 вопросов, поведение судьи), что не получилось.

**Шаг 9. Финальная проверка.** Запусти всё с чистого клона по инструкции из README. Убедись, что в репозитории нет ключей и корпуса, а в Langfuse видны трейсы всех прогонов. В финальном сообщении дай человеку: ссылку на репозиторий, таблицу метрик, три худших ответа с разбором причин и список того, что ему нужно проверить руками.

## Правила исполнения
- Не выдумывай числа: всё, что попадает в README, берётся из результатов прогонов.
- Перед каждым платным массовым вызовом оценивай стоимость и держи общий расход на проект в пределах, о которых договоришься с человеком в начале.
- Каждый шаг заканчивается проверкой, которую можно выполнить командой (сколько страниц, какой hit@5, есть ли трейсы в Langfuse).
- Если шаг заблокирован, сообщи причину и продолжай со следующим, который от него не зависит.
